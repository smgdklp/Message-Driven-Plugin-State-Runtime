## 1. 这个项目是什么

一个**消息驱动 + 状态托管 + 多线程分流**的 Windows 插件运行时。

宿主进程只负责五件事：

1. 管内存池（`Pool_msg` / `Pool_map` / `Pool_state` / `Pool_dll`）
2. 管线程池与 dispatcher 池（`Pool_thread` / `Pool_dispatcher`）
3. 管引用计数（`Map` 里的 `Countptr`）
4. 把字节流按 handle 分发出去（`Queue` + `Dispatcher`，**一条队列一条常驻线程**）
5. 按清单装载 / 卸载插件（`plugin_load` / `plugin_unload`）

**所有业务逻辑都是插件**——包括"加载和卸载插件"这件事本身（那是内核组件
[DLLMgr](DLLMgr内核组件.md) 干的）。宿主里没有一行关于 capture、cmd 或任何具体
功能的代码。

```
                        ┌────────────────────────────────────────────────────────┐
  build/config.json     │  mdpsr.exe                宿主 Runtime                  │
  { "plugin": […],      │                                                        │
    "init_cmd": "…" }   │  池: Pool_msg  Pool_map  Pool_state  Pool_dll          │
        │               │      Pool_thread (线程)  Pool_dispatcher (dispatcher)  │
        │               │                                                        │
        ├──────────────▶│  ① plugin_load: 预加载 plugin 列表                     │

          后门点火       │                                                        │
                        │  每个 Queue* 一条常驻线程, 线程上跑它自己的 Dispatcher: │
                        │  ┌────────────┐ ┌──────────────┐ ┌────────────┐        │
```

## 3. 四条基本约定

这四条是整个设计的地基，改任何东西之前先读它们。

### 3.1 消息只是字节流

一条消息在队列里序列化为连续字节：

```
偏移 0    int32_t  _len       本条消息的总字节长 (= 12 + body)
偏移 4    uint64_t _handle    目标 handle 的哈希值
偏移 12   uint8_t  _buffer[]  附带信息, body 长度 = _len - 12
```

**Dispatcher 只做一件事**：按 `_handle` 查表，把「上下文 + 后面的字节」原样交给 handle。

字节部分怎么解析，完全由各组件自己约束，宿主不做任何解释。
每个组件在自己的文档 / 头文件里声明自己期望的载荷布局，例如：

| 载荷 | 谁定义 | 布局 |
| --- | --- | --- |
| `mdpsr_ctrl_msg` | `abi.h` 通用 | `{int32 cmd; int32 flags; uint64 arg; char text[240];}` |
| `mdpsr_dllmgr_cmd` | DLLMgr | `{int32 _cmd; uint32 _pad; uint64 _dll; char _path[];}` |

因为 `_len` 是"本条消息的**总**字节长"，所以"队列中可读字节数 >= `_len`"
就是"积累出一条完整消息"的判据——这也让写一半的并发生产者天然安全。

### 3.2 State 是公用配置 / 公用数据对象

`State` 不只是可变长 cache。它的定位是：

> **DLL 对外暴露的公用配置 / 公用数据对象。**

凡是需要跨组件公用、需要**防止别人直接索引自己的类而造成依赖打结**的东西，
都必须挂成 `State` 交给 `Map` 托管，而不是让别的插件去摸自己的类实例。

* 载荷长度可变（`mdpsr_state.payload` + `size`）只是它的能力之一；
* 载荷是任意字节，由创建它的 state 工厂自行解释；
* `kind` 是插件自定义的类型标签，方便接手的插件辨认载荷；
* `destroy` 是可选钩子，让载荷内部持有的资源能被正确收尾；
* 一个 handle 可以同时绑定最多 `MDPSR_MAX_BIND_STATES`（4）个 State。

### 3.3 Handle 是解耦接口，必须无状态

Handle 一般充当接口层：它把"谁能被消息驱动"这件事暴露出去，
把具体实现（object）和具体数据（state）解耦开。

* handle 函数**必须无状态**——不依赖、不修改任何可变全局量；
* 只通过 `msgData / msgLen` 与 `ctxData / ctxLen` 工作；
* 按约定，**非 cache 的状态一律放 State**，handle 只做转发和参数校验。

DLLMgr 就是一个典型例子：handle 只负责把字节流解析成 `{cmd, dll, path}`
并转交给 `DLLMgr` 对象，真正做事的是对象，数据在三个 State 里。

### 3.4 分流：一个 Dispatcher 只吃一个 Queue

`Map` 里除了 `State*` / `Classptr*` / `Handle*`，还**并列挂着 `Queue*`**
（`MDPSR_ENTRY_QUEUE = 4`）——这是 Map 的第四类条目。

* **每个 Queue 与一个 Dispatcher 生命周期绑定**，一个 dispatcher
  只从自己那一个 queue 取消息；
* 组件可以在 `plugin.json` 的 `queue` 段**申请自己的队列和名字**
  （宿主会给它建 Queue + Dispatcher + 一条常驻线程），
  再把 handle 用 `"queue": "队列名"` 绑上去；
* 于是发给那些 handle 的消息就在**那条专属线程**上执行——这就是"分流"；
* **组件卸载时，属于它的队列与线程一起卸载**；
* **投喂失败一律回退 `queue_core`**：找不到绑定的队列、队列已失效、
  或者组件干脆没声明队列，都走默认的 `queue_core`；
* **所有组件都能从上下文拿到发起本次分发的 `Map.Queue*`**
  （`mdpsr_content::queue` / `mdpsr_core_content::queue`），
  往它里面投消息就等于"把活儿留在自己的线程上"。

分流的本质：**每个 dispatcher 做的事情完全一样**（取消息 → 查表 → 组 ctx → 调 handle），
区别只在"吃哪个队列"。所以它是一个纯粹的**横向分流**机制，
不需要为每个业务写一套调度逻辑。

## 4. 内存池 / 线程池 / dispatcher 池

| 池 | 类型 | 职责 |
| --- | --- | --- |
| `Pool_msg` | `std::pmr::synchronized_pool_resource` | 消息字节流（`Queue` 的环形缓冲与落地缓冲），以及分流队列本体 |
| `Pool_map` | `std::pmr::synchronized_pool_resource` | `Map` 的节点与 `Countptr` 计数指针、`dllptr` 与 `mdpsr_queue` 描述符 |
| `Pool_state` | `std::pmr::synchronized_pool_resource` | 跨 DLL 共享的 State 载荷、插件描述符 |
| `Pool_dll` | `std::unordered_map<uint64_t, unique_ptr<synchronized_pool_resource>>` | **每个 DLL 一个独立池**，卸载时整池释放 |
| `Pool_thread` | `ThreadPool` | **挂载 dispatcher 的线程池子**：每条分流队列从这里拿一条常驻线程 |
| `Pool_dispatcher` | `DispatcherPool` | **存放 dispatcher 对象**：一个 dispatcher 对应一条队列 |

> **`Pool_state` 已从 `unsynchronized_pool_resource` 改成 `synchronized_pool_resource`。**
>
> 这是对原始需求的一处**有意偏离**：原设计写的是 `unsynchronized_pool_resource`，
> 但适配多线程分流之后，多条分发线程会**并发**从它分配 State 载荷，
> 而跨线程使用 `unsynchronized_pool_resource` 是未定义行为。
> 所以这里换成了同步版本；名字仍然叫 `Pool_state`，语义不变。

`Pool_dll` 是"卸载即整池回收"的关键：插件在自己的专属池里 new 出来的所有东西，
只要不跨池引用，卸载时一次性 `reset()` 就干净了，不用逐块 free。

## 5. Map 与引用计数

```cpp
struct Countptr {
    void*    ptr;            // State* / Classptr* / Handle* / Queue*
    int32_t  r_count;        // 在读计数
    int32_t  w_count;        // 在写计数
    int32_t  valid;          // false 时一律视为不存在
    int32_t  type;           // mdpsr_entry_type
    uint64_t dll;            // 所属 dll 键
    uint64_t bind_object;    // handle 专用: 绑定的 object 键
    uint64_t bind_queue;     // handle 专用: 绑定的分流队列键, 0 = queue_core
    uint32_t bind_state_count;
    uint64_t bind_states[4]; // handle 专用: 绑定的 state 键
    char     name[64];
};
```

条目的类型：

```c
enum mdpsr_entry_type {
    MDPSR_ENTRY_STATE       = 0,
    MDPSR_ENTRY_OBJECT      = 1,
    MDPSR_ENTRY_HANDLE      = 2,
    MDPSR_ENTRY_HANDLE_CORE = 3,
    MDPSR_ENTRY_QUEUE       = 4     // Map.Queue*, 与上面三类并列
};
```

* 键 = `mdpsr_hash64(条目名称)`，**名称必须全局唯一**
  （同一个 dll 里 handle 和 object 不能同名，否则后注册的那个会拿到
  `MDPSR_ERR_ALREADY_EXISTS`）。
* 分发前 `acquire()`（`r_count++`），调用返回后 `release()`，
  所以卸载流程可以精确等到"没人再用"。
* `invalidate()` 把 `valid` 置 0 后，任何 `acquire()` 都会返回
  `MDPSR_ERR_MAP_INVALID`，用来"阻止新的读取"。
* `bind_queue` 决定 `emit()` 把消息投到哪条分流队列；`0` 表示走 `queue_core`。

## 6. 分发流程

多线程之后，**消息不再由宿主主线程泵**，而是由**各分流队列自己的常驻线程**
（从 `Pool_thread` 拿）调用 `Runtime::dispatch_message`：

```
每条分流队列的常驻线程:
    Queue::pop()  ──▶  Runtime::dispatch_message(dispatcher, handle, body, len)
                              │
                              ├─ 按 bind_states[]  逐个 acquire  ──▶ mdpsr_state_slot[]
                              ├─ 按 bind_object    单个 acquire  ──▶ mdpsr_classptr*
                              │
                              ├─ queue = 这条 dispatcher 自己的 mdpsr_queue*
                              │  (handle_core 还额外拿到 queue_all = 全部分流队列快照)
                              │
                              ├─ handle_core ?  mdpsr_core_content { state, classptr, handle,
                              │                                      handle_core, classptr_all,
                              │                                      dllptr, host,
                              │                                      states[], state_count,
                              │                                      queue, queue_all }
                              │              :  mdpsr_content      { state, classptr, host,
                              │                                      states[], state_count,
                              │                                      queue }
                              │
                              └─ fn(msgData, msgLen, &ctx, sizeof(ctx))
                                     │
                                     └─ 返回后逐个 release，再 release handle 本身
```

* 一个 dispatcher 只从**一个**队列取消息，所以同一个队列上的消息天然串行；
  不同队列之间是**真并发**。组件自己线程里的共享数据要自己加锁。
* 异常绝不允许穿过 DLL 边界：`dispatch_message()` 外面套了一层 `try/catch`。
* `Content::queue` / `states` / `classptr_all` / `queue_all` 都**只在本次调用期间有效**，
  返回后失效，别存下来。

## 7. 初始化流程

```
1. 完成原有池子 (Pool_msg / Pool_map / Pool_state / Pool_dll)
   + 新增池子 (Pool_thread 线程池 / Pool_dispatcher dispatcher 池)
   + Map 的初始化
2. 读取 exe 同目录的 config.json:
       "plugin"   : 要预先加载的插件 plugin.json 相对位置列表
                    (相对运行时根目录 = exe 所在目录)
       "init_cmd" : 后门级别函数的标签, 宿主直接 GetProcAddress 调用它
3. 逐个 plugin_load:
       解析清单 → LoadLibrary → mdpsr_module_init → 建专属池
       → 建组件申请的分流队列 (Queue + Dispatcher + 常驻线程)
       → 调 state 工厂并注册 → 调 object 工厂并注册
       → 注册 handle 并绑定 state / object / 分流队列
4. 调用 init_cmd 后门 (内核 DLL_init 建立 queue_core + 它的分发线程,
   再把第一条 cmd=0 投进队列)
5. **主线程不再泵消息** —— 每条分流队列都有自己的常驻线程在跑 dispatcher,
   主线程只等运行时长
6. 向 queue_core 注入 DLLMgr cmd=3 (清空区域) 等它异步收敛,
   然后停掉所有分发线程, 卸载模块
```

当前项目的 `scr/main/config.json`：

```jsonc
{
  "_comment": "宿主 exe 同目录的初始化配置。plugin = 要预先加载的插件清单(相对本文件/运行时根目录); init_cmd = 后门级别函数的标签, 宿主会在所有已加载模块里 GetProcAddress 找到同名导出并直接调用(不经过消息队列)。",

  "plugin": [
    "core/plugin.json"
  ],

  "init_cmd": "DLL_init"
}
```

> **早先那个十六进制 `"message"` 消息列表已经废弃不用了。**
> 现在点火靠的是 `init_cmd` —— 一个**后门级别函数的标签**：宿主在所有已加载模块里
> `GetProcAddress` 找到同名导出，然后**直接调用**它（不经过消息队列）。
> 当前内核组件 DLLMgr 导出的 `DLL_init` 就是这个后门，它负责建立 `queue_core`
> 并把第一条 `cmd=0` 投进去。详见 [DLLMgr 内核组件](DLLMgr内核组件.md)。

`config.json` 里**只预加载 core**。capture / cmd 两个插件是 DLLMgr 读了自己的
`DLLMgr_link` 之后，把它们变成加载消息投进 `queue_core` 装进来的——
这条链路本身就是"宿主不关心业务"的最好证明。

## 8. 加载 / 卸载时序

### 加载 `plugin_load(manifest_rel)`

```
0. load_manifest: 解析 plugin.json, 缓存 (dll 键 = mdpsr_hash64(manifest 相对路径))
   解析顺序: queue 段 / state 段 / object 段 / handle 段
1. 对清单里每个 dll_path:
       LoadLibraryW → 轮询等 mdpsr_abi_version() 与宿主一致 (最多 3 秒)
       → 调 mdpsr_module_init(host_api, dll)
2. dll_pool_create: 给这个 dll 建专属池
3. queue  : 组件申请的分流队列。若条目给了 symbol 就先调 queue 工厂
            (ctx{..., pool=Pool_msg, host}) 拿 mdpsr_queue_desc
            (capacity / flags), 工厂返回非 OK 就跳过这个队列;
            然后 queue_create(name, capacity, dll, core=false, &q)
            → 建 Queue + Dispatcher + 常驻线程, 注册成 Map.Queue*
4. state  : ctx{name,param|list,manifest,manifest_dir,dll,pool=Pool_state,host}
            → 工厂返回 mdpsr_state* → 以 hash(名称) 为键注册进 Map
5. object : ctx{..., pool=该 dll 的专属池}
            → 工厂返回类实例 → 包成 mdpsr_classptr 注册进 Map
            → 若导出了 <symbol>_destroy, 记进 classptr->destroy
6. handle : 分配 mdpsr_handle_core → 填 fn/name/kind → 注册,
            把清单里的 "states" / "object" / "queue" 解析成键写进
            bind_states / bind_object / bind_queue
            (queue 名字找不到对应队列时, 打日志并回退 queue_core)
7. 把上面所有键记进 dll -> keys 索引 (供 plugin_keys 与卸载使用)
```

### 卸载 `plugin_unload(dll)`

```
0. 趁条目还有效, 先把 (键, 类型, 指针) 抄一份出来
   —— 一旦 invalidate, map_lookup 就会拒绝访问, 所以必须提前取
1. 统一 invalidate: 阻止新的读取
2. 等所有资源 r_count / w_count 归零 (每个键 5 秒, 再加一次 dll 级等待)
   超时则中止并返回 MDPSR_ERR_PLUGIN_BUSY
3. 把这个 dll 的分流队列摘出来并置停:
   如果发现"队列在自己的分发线程上被要求销毁"(会自 join 死锁),
   就塞回去并返回 MDPSR_ERR_PLUGIN_BUSY
4. **锁外 join 这些线程** —— 那条线程可能正卡在 _plugin_mtx 上等我们,
   join 必须放到 _plugin_mtx 之外做, 否则死锁
5. 依次收尾: object → 调 destroy → 释放描述符
             state  → mdpsr_state_delete (会先跑 st->destroy)
             handle → 释放描述符
6. 释放队列槽位: dispatcher → Queue → mdpsr_queue 描述符 (线程已 join)
7. 摘除剩余的 Map 条目
8. 整池释放该 dll 在 Pool_dll 里的池
9. 卸载模块: mdpsr_module_fini + FreeLibrary
```

| --- | --- | --- |
| `queue` | `Capture.Thread` | 组件自己申请的分流队列（`capacity: 8192`，工厂 `mdpsr_queue_capture`） |
| `state` | `Capture.SavePath` | 保存路径 string，**默认 `./test/img`** |
| `object` | `Capture.Screen` | `WinCapture` 的插件包装（专属池里 new） |
| `handle` | `Capture.Cmd` | 绑定上面两个，并 `"queue": "Capture.Thread"` |

命令：`1` 设 HWND / `2` 设 FPS / `3` 开始连续截屏 / `4` 暂停 / `5` 单帧 /
`6` 设保存目录 / `7` 设文件名前缀 / `8` 设落盘间隔 / `9` 状态 / `10` 停止释放。

> `Capture.Cmd` 绑在自己的分流队列 `Capture.Thread` 上，
> 所以它的消息**在截屏自己那条线程里跑**，不占用 `queue_core`。

### 9.2 仿真 cmd 插件（`Cmd.*`）

| 类型 | 名称 | 说明 |
| --- | --- | --- |
| `state` | `Cmd.Script` | 脚本路径（默认 `coment.json`）+ 行游标 / 播放状态 |
| `object` | `Cmd.Sim` | GDI 假 cmd 窗口（自带消息泵线程） |
| `handle` | `Cmd.Cmd` | 绑定上面两个（没声明 `queue`，所以走 `queue_core`） |

命令：`1` 播放 / `2` 暂停 / `3` 单步 / `4` 重置 / `5` 换脚本 /
`6` 设行间隔 / `7` 显示 / `8` 隐藏 / `9` 状态 / `20` **把 HWND 广播给 `Capture.Cmd`** /
`21` 广播给指定 handle。

`cmd 20` 就是两个插件"协同工作"的接口：cmd 插件不知道截屏插件内部长什么样，
截屏插件也不认识 cmd 插件，它们只通过宿主的消息总线交换一个 HWND。

## 10. 测试

`/test` 下每个文件夹都是一个独立测试项目，各自带 `CMakeLists.txt`，
能单独配置、编译出完整的可执行测试（它们会 `add_subdirectory(scr/main)`，
把整套项目一起构建，再链接运行时静态库 `mdpsr_runtime`）。

```powershell
pwsh -File test\run_all.ps1                 # 全部
pwsh -File test\run_all.ps1 -Test mt        # 只跑一个
```

| 测试 | 覆盖 |
| --- | --- |
| `test/queue` | 帧语义：FIFO、二进制安全、扩容、环形回绕、`push_frame` 校验 |
| `test/mt` | 多线程读写压力：4 条队列并发投喂 4 万条、Map 引用计数、并发造 State、并发建销分流队列 |

### `test/mt` 的 6 个阶段

`test/mt` **不加载任何插件、也不读 `config.json`**，只链接 `mdpsr_runtime`，
纯粹打运行时本身：

| 阶段 | 干什么 | 验什么 |
| --- | --- | --- |
| 1 | 起 `queue_core`，再起 4 条自定义队列（`mt.q0` ~ `mt.q3`） | 分流线程数 = 5；`queue_core()` / `queue_list()` 都能取到 |
| 2 | 4 个生产者线程并发往 4 条队列投喂 **4 万条**（`kMsgTotal`），每条带一个递增 `uint64` | 全部被消费；条数一条不多一条不少；**求和**与**异或**都和理论值一致（能查出丢包 / 重复 / 串值）；四条队列的消化量之和 = 总数 |
| 3 | 8 线程 × 2 万次反复 `map.acquire` / `map.release`（读、写各一轮） | 压力结束后所有条目 `r_count == w_count == 0` |
| 4 | 8 线程 × 400 次并发 `mdpsr_state_new`（从 `Pool_state`）+ 注册 + 摘除 + `mdpsr_state_delete` | 全部成功，且临时条目没有泄漏在 Map 里 |
| 5 | 4 线程 × 15 次并发 `queue_create` + 投一条 + `queue_destroy` | 全部成功；收拾后仍剩 5 条分流线程（考验 `Pool_thread` + `Pool_dispatcher`） |
| 6 | `stop_dispatchers()` 后汇总 | 分流线程全清、Map 只剩测试 handle、`dispatch_errors == 0`、**`fallback_total == 0`**（证明分流真的分流了，没有回退 `queue_core`）、入队计数合理 |

详见 [../test/README.md](../test/README.md)。

## 11. 错误码

| 区间 | 含义 |
| --- | --- |
| `11001`–`11015` | 通用（未知命令 / 配置无效 / 空指针 / 类型不匹配 / 创建失败 / 超时 / 忙 / 载荷非法 …） |

## 12. 本机环境约定

| 工具 | 位置 |
| --- | --- |
| CMake | `D:\Cpp\cmake`（`bin\cmake.exe`，已挂进机器 PATH） |
| MSVC | Visual Studio Community 2026，装在 `D:\Program Files\vs`（`vswhere` 能探到） |
| VS 组件清单 | `C:\Users\ThinkPad\Documents\.vsconfig` |
| 生成器 | 默认 **`Visual Studio 18 2026`（MSBuild）+ `-A x64`** |
| C++ 包 | `D:\Cpp\Packages`（OpenCV 在 `D:\Cpp\Packages\opencv`） |
| CUDA | `D:\Cpp\CUDA`（`CUDA_PATH` 指向 `D:\Cpp\CUDA\v13.3`） |

> **为什么不用 Ninja**：中文版 MSVC 的 `/showIncludes` 前缀经过码页转换后
> 与 `cl.exe` 实际输出对不上，会让 Ninja 的依赖库变成空的（改头文件不重编）。
> 所以默认走 MSBuild；真要用 Ninja 必须先把依赖跟踪修好。

`build.ps1` 会按上面的顺序自动探测；找不到时会明确告诉你该装到哪里。
