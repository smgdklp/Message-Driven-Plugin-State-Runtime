# mdpsr 架构说明（ABI v3）

> ★ 这篇讲**框架层**：锁序、生命周期、为什么不会死锁。
> **GUI 不在宿主里** —— GUI 插件、可调参数、4 通道图像约定、事件协议见 [GUI.md](GUI.md)。

## 一、模块划分

```
src/main/
├── include/mdpsr/abi.h     ★ 唯一的二进制契约 (纯 C99, 只有 POD + 函数指针)
└── runtime/
    ├── registry.{h,cpp}    条目表 + 每插件池 + 代际 + 借还协议 + 上线门闸 (核心)
    ├── queue.{h,cpp}       有界环形队列 + 限速 + 一条队列一条线程
    ├── runtime.{h,cpp}     生命周期编排: init/boot/shutdown/watchdog/路由/分发
    ├── loader.{h,cpp}      清单解析 + 装载/卸载/重载状态机
    ├── host_api.cpp        函数表 30+ thunk + 逐字段装配校验
    └── json.{h,cpp}        严格的只读 JSON

src/components/             winmsg (GUI broker) + 演示插件
test/                       ★ 测试模块 (不进 src): 三个纯色圆 GUI 客户端 + GUI 自测
├── gui_test_protocol.h     三个测试插件的参数表 + 参考光栅器 (插件与自测共用一份)
├── gui_client_common.h     三个测试插件的公共实现
├── circ_a/ circ_b/ circ_c/ 各自独立编译, 产物落 build/plugins/<名字>/
└── gui_selftest.{h,cpp}    GUI 阶段的全部断言 (宿主只调一个入口)
```

四层各管一件事，互相不越界：

| 层 | 管什么 | 不管什么 |
| --- | --- | --- |
| `Registry` | "一个名字对应一块资源，谁能借、怎么还、什么时候失效、什么时候上线" | 谁装的、装到哪一步 |
| `Queue` | "一条有界的字节流 + 一条线程 + 限速" | 消息是什么意思 |
| `Runtime` | "路由一张表、编排一次装载的每一步、把消息派给 handle" | 条目内部是什么类型 |
| `Loader` | "清单说什么、DLL 导出什么、失败怎么回滚" | 分销细节 |

## 二、四条不变量

### 1. 控制块永不释放

`Registry::Entry`（和 `PluginRecord`）**只分配、不释放**。卸载时把 `gen` 置 0、
把 `ptr` 清掉，但这条记录本身永远在。

为什么：**只要控制块还活着，插件手里的 `key` 就永远不会变成悬垂指针**。于是"资源随时
可能因为别人卸载而消失"这件事，可以被一个纯粹的值比较（`gen` 对不对）表达出来，
而不需要引用计数、不需要读写锁、不需要插件做任何配合。

代价是每次装卸留下一条记录（几十字节），换来的是整个生命周期的可证明性 —— 值得。

### 2. `gen` 表达"这是第几代"，`published` 表达"上线了没有"

* `gen` 每次成功装载 +1，**0 表示无效**（正在卸载 / 已卸载）。
* `published` 是第二个闸门：`attach` 的时候条目已经挂上表了（`gen` 也有值），但
  `published = false`，**谁也借不到**；整个插件装好、要宣布 READY 的那一刻，
  `Registry::publish()` 一次性把它名下所有条目翻成可借。

为什么要有第二个闸门：装载失败的回滚要 `pool_delete`（整池还给系统）。如果半装好的
State 已经能被别人借走，那个借阅方手里的载荷就会在池回收时变成悬垂 —— 而回滚时我们
**不一定抢得齐**所有条目锁。上线门闸把这条路径从"抢不到锁就危险"变成"根本不可能有人
拿着"。同一条闸门还顺手统一了另外两件事：

* `gen_of` / `kind_of` 对没上线的条目返回"不存在"（探活问的是"服务在不在"，半装好的不算服务）；
* 分发路径**拒绝调用没上线的 handle**：那不是死信，是"马上要来的服务"，回 `BUSY` 让消息
  回滚重投，等它上线下一轮再跑。

### 3. 借还协议 = 一把非递归锁 + 一本台账

```c
acquire(host, key, want_gen, &ptr, &gen);   // 借到 = 持锁 (timed_mutex)
release(host, key);                          // 归还
release_all(host);                           // 归还本次调用借的全部
gen_of(host, key);                           // 无锁探活
```

* **每线程一本台账**（`Tls` 里的 journal）：记着"我借了哪些 key"，顺序都在里面。
* **同一线程里多次 `acquire`，键必须严格递增**，否则 `LOCK_ORDER`（11014）。
  一次要借多个用 `acquire_many`，宿主内部排序。这条规则把"插件之间互相咬锁"的
  死锁在**结构上**消灭掉了（见第三节）。
* **分发路径上那把 handle 锁刻意不进台账**：它由宿主直接 `try_lock`，不参与"按键升序"
  这条规则。否则键是哈希（近似随机），任何 handle 借自己的 State 都有一半概率被
  `LOCK_ORDER` 拒掉 —— 这是让第三节那条规则不至于把插件逼死的必要一环。
* 宿主**每次调用插件代码**都开一个 `CallScope`；作用域退出时如果台账里还有没还的锁，
  宿主替它还掉并记一条 WARN。**所以"插件漏锁把运行时卡死"不可能发生。**

### 4. 管理面（装卸）对插件代码永不阻塞

装卸由 `_ctrl_mtx` 串行化。**宿主自己**（调用深度 0）照旧老实等锁；**插件代码**
（正跑在某条队列线程的 handle 里，深度 > 0）只 `try_lock` 一次，拿不到立刻返回
`BUSY`，由调用方下轮再来（内核组件 `sysmgr` 就是这么重试的）。

为什么必须这样：卸载路径全程持着 `_ctrl_mtx` 去 `join` 队列线程。插件代码要是也阻塞在
那把锁上，就形成"我等你放锁、你等我退出"的环 —— 这是整个运行时里唯一还能闭合的等待环，
第四节把它堵掉了。

## 三、锁层次与死锁自由性

### 3.1 五种锁

| 锁 | 保护什么 | 谁拿 | 能不能阻塞等待 |
| --- | --- | --- | --- |
| `_ctrl_mtx`（管理面） | 装卸/重载串行化 | 宿主 + 内核插件 | 宿主能；**插件代码不能**（try 一次，失败给 BUSY） |
| `_plg_mtx` | 插件记录表的形状 | 所有线程 | 能，短暂（绝不在持有它的时候 join） |
| `_reg._mtx`（注册表） | 条目表的桶 | 所有线程 | 能，但**绝不跨越等待别的锁** |
| `Entry::mtx`（条目锁） | 那一条资源 + 它的载荷 | `acquire` / 分发路径 | **有界**（见 3.3） |
| `Queue::_mtx` | 那条环形缓冲 | 生产者/消费者 | 能，短暂（纯内存操作） |

### 3.2 为什么不会死锁：等待边只有三类

整个运行时里"持着 A 去等 B"的边只有三条，而且都指向**叶子**：

```
注册表锁  ->  条目锁        (find 之后要锁那一条)
条目锁    ->  (什么也不等)   ← 叶子
队列锁    ->  (什么也不等)   ← 叶子
```

**没有任何一条边反向指回去**，所以不可能成环。这是设计出来的，不是碰巧：

* `acquire` 拿条目锁之前**先放掉注册表锁**；
* 卸载路径**先把所有锁抢齐**，再去做需要等待的事（停队列、join、`_destroy`）；
* 队列的 `push`/`pop` 只在队列锁里做纯内存操作，不会去等条目锁；
* **唯一危险的形状是"持着锁去 join"**：卸载路径持着 `_ctrl_mtx` 去 join 队列线程，
  所以插件代码**不许**在那把锁上阻塞（第二、四节）；
* GUI broker 额外守一条：**`Screen` 与 `Surface` 永不嵌套持有**（见 [GUI.md](GUI.md) 第七节）。

### 3.3 关键的一步：等待都有上界

`Entry::mtx` 是 `std::timed_mutex`，所有等待都走 `lock_bounded()`：

```
try_lock()  ->  成功就再查一次 gen (查完发现失效就立刻放锁)
            ->  仍然有效才 try_lock_for(MDPSR_LOCK_WAIT_MS = 50ms)
            ->  反复 MDPSR_LOCK_TRIES = 8 次
            ->  还是拿不到 -> MDPSR_ERR_BUSY (11011)
```

**顺序很重要**：先拿到锁、再看 `gen`。反过来（先看 `gen` 再去阻塞等锁）就是当年那个
死锁的形状（见第九节）。

`BUSY` 不是错误，是**"下轮再来"**：调用方（队列分发器、卸载路径、`sysmgr`）都认这个码，
把消息重投、把卸载推迟。

### 3.4 借不到锁不是错

这条看着小，其实决定了整个系统的"手感"：

* 队列线程分发一条消息时，如果目标 handle 的锁正被卸载方握着 → `BUSY` → **消息回滚重投**，
  不是丢、不是报错（`t_busy_requeue` 计数器盯着这件事）。
* 卸载时抢不齐锁 → `PLUGIN_BUSY`，`sysmgr` 下轮再来。
* 于是"正在卸载"和"正在发消息"可以自然搓开，谁也不用等谁。

## 四、消息的生命周期

```
emit(dst, cmd, body, len)
  ├─ dst 是不是本插件自己的 handle? 不是 -> 查路由表 (handle -> queue)
  ├─ 队列满 -> QUEUE_FULL, 直接返回 (不阻塞、不替你缓冲)
  ├─ 入队 (一条 24 字节头 + body, 拷进环形缓冲)
  └─ 唤醒那条队列的线程

队列线程 run():
  ├─ 限速: 距上次"处理开始"不足 pace_ms -> 睡到点 (自己的线程, 睡得起)
  ├─ pop 一帧
  ├─ dispatch_frame():
  │    ├─ 目标不存在 / gen == 0  -> 死信: 回 FAIL 给 src (src=0 就不回)
  │    ├─ published == false     -> 插件正在装载: 消息回滚重投 (BUSY, 不是死信!)
  │    ├─ 有界等待目标 handle 锁 (先 try, 失败再看 gen; 仍然有效才有界等待)
  │    │    ├─ BUSY(等满上界) -> 死信 + FAIL_REJECTED
  │    │    └─ 等锁期间被置无效 / 队列在停 -> 死信
  │    ├─ 调 handle(msg, body, len, ctx)   ← 在 CallScope 里
  │    │    └─ 返回 BUSY -> 消息回滚重投 (t_busy_requeue++)
  │    ├─ 退出 CallScope: 台账里还没还的锁由宿主兜底还掉并记 WARN
  │    └─ release
  └─ 统计 popped/errors/...
```

**保留命令**：`0 INIT`、`1 REPLY`、`2 FAIL`、`3 PING`、`4 PONG`、`5 STOP`；
插件自己的命令从 **16** 开始。`REPLY`/`FAIL` 是"请求-回包"的全部机制
（异步，没有阻塞等回复的 API）。

**死信**：投给一个已经不在的 handle 会回一条 `cmd=FAIL` 给 `src`（宿主自己发的 `src=0`
就不回）。自测里的"死信 2492"就是卸载期间的正常现象。

## 五、热插拔状态机

### 5.1 装载 `plugin_install`

```
1  解析清单 (严格 JSON: 未知字段 / 类型错都拒绝)
2  检查条目名全局唯一 (撞名直接拒绝; 固定队列名除外)
3  建每插件池 (std::pmr::synchronized_pool_resource)
4  装 DLL + 核对 mdpsr_abi_version (对不上直接拒绝)
5  mdpsr_module_init
6  队列 (清单声明的, 工厂给 capacity/pace_ms)
7  State  (工厂从 ctx->pool 分配; **挂上表但 published=false**)
8  Object (同上)
9  Handle (登记进注册表; 按清单绑队列, 默认 Queue_default; 同样还没上线)
10 上线: publish(全部条目) --> READY, gen = 上一个 gen + 1
11 (默认) 在**调用者线程**上同步跑一次 Init handle 的 cmd=0
```

任何一步失败都**逐级回滚**（析构已经建好的条目、停并 join 已经起的队列、卸 DLL、
销毁池），然后返回错误码 —— 不是"装载成功但少了一半资源"。

★ 第 7~9 步建出来的东西**在装载成功之前谁也借不到**（第 10 步的 `publish` 才上线）。
   所以回滚里那句 `pool_delete` 是安全的：不可能有人手里攥着一个半装好的载荷。
   （这是本轮修掉的一个真问题：以前回滚时"抢不齐锁也照样整池回收"，理论上能把
   借阅方手里的内存还回系统。）

第 11 步那条要记住：`cmd=0` 里**不能假设自己在自己的队列线程上**。
需要线程亲和的初始化（比如起一条 GUI 线程）可以，但不能假设"我就是那条线程"。

### 5.2 卸载 `plugin_uninstall`

顺序是这个系统里最讲究的一段（改它之前先读第九节）：

```
1  hold_kind(HANDLE)        ← 先独占全部 handle
2  invalidate_all           ← 再统一置 gen = 0
3  hold_except_kind(HANDLE) ← 抢其余条目 (State/Object/Queue)
4  release 其余 (保留 handle 锁)
5  stop + join 每条队列线程
6  逐个调 _destroy (State/Object)
7  摘表 (detach)
8  mdpsr_module_fini + FreeLibrary
9  pool_delete  ← 整池回收
10 release handle 锁 (最后)
```

**为什么不能"先置无效再抢锁"**：那样会开出一个窗口 —— 在途的 handle 拿到一个
"gen 已经是 0，但资源还没收"的插件，于是返回一堆莫名其妙的错误码（当年是 12002）。
**为什么先抢 handle**：handle 是消息入口，先把它独占住就等于"新的分发进不来了"，
而这时候**什么都还没改**，抢不到就干净地 `PLUGIN_BUSY`。

★ 这段全程持有 `_ctrl_mtx`（管理面），而第 5 步里有 `join`。所以**插件代码不许阻塞
   在这把锁上**：拿不到就 `BUSY` 走人（见第二、四节）。另外队列归属也收紧了：
   `queue_bind` 只能绑自己的 handle 到自己的（或宿主的）队列上；运行时 `queue_create`
   遇到"名字被别人占了"返回 `ALREADY_EXISTS`，不会把别人的队列登记成自己的。
   —— 这两条一起把"卸载 X 却在 join 别人的队列线程"这种形状关掉了。

### 5.3 重载 `plugin_reload`

= 卸载 + 重新装载，`gen` 会 +1。卸载之后能重新装回来，这是 v1 做不到的
（v1 文档把"代际"列为重载的前置难题）。

## 六、内存模型

| 内存 | 从哪来 | 谁释放 | 装什么 |
| --- | --- | --- | --- |
| 宿主 arena | `std::pmr::synchronized_pool_resource` | 进程退出 | 条目控制块（**永不释放**）、固定队列、插件记录 |
| 每插件池 | `std::pmr::synchronized_pool_resource`（`ctx->pool`） | **卸载时整池 `pool_delete`** | 该插件的 State/Object/Queue/DLL 侧对象 |
| 消息缓冲 | 队列自己的 `pmr::vector` | 队列销毁 | 帧字节 |

规则只有一条：**工厂里一律用 `ctx->pool` / `mdpsr_fctx_alloc`，不要 `new` / `malloc`。**
用了池，卸载时"这个插件占的内存全回来了"就是一句话的事；混用就漏。
自测每轮核对"条目/队列精确回到基线"，池是否整池回收由那次核对间接证明。
（`pool_alloc` 和 `pool_free` 都会校验"这是不是你自己那个池" —— 只有一半被保护等于没保护。）

> GUI 画面（那块 4 通道 BGRA 内存）也遵守这条：由客户端在自己 State 的工厂里从
> `ctx->pool` 里出，所以"客户端一卸载，图就跟着池一起没了"不需要额外机制保证 ——
> broker 那边靠 `acquire` 把它钉住不让它中途消失。见 [GUI.md](GUI.md) 第三节。

## 七、队列与限速

* **有界**：`capacity` 是硬上限，满了 `push` 返回 `QUEUE_FULL`。投递方必须自己认这个错误
  （自测里的捣乱线程就是满了就退让 5 倍时间）。
* **限速**：`pace_ms` 是"两条消息的**处理开始时间**"之间的最小间隔。实现是
  `next_allowed = 上一条的开始时间 + pace_ms`，所以处理耗时不会被累加进去。
  宿主在 `init` 里 `timeBeginPeriod(1)`，否则 Windows 的 sleep 粒度 ~15.6ms 会让
  "声明 20ms 实际跑成 ~31ms"。
* **每条队列一条自己的线程**（v3）。以前还有"挂宿主主线程、由主循环泵"的模式，已经删掉：
  它是全框架唯一零测试覆盖的路径，而宿主主线程现在什么也不管了。
* **统计**：`pushed / popped / full / paced / errors / high_water` 都是真的，
  `host->queue_stats` 能取到（v1 的"限速挡下"计数器压根没人加过）。

已知取舍：队列严格 FIFO、**没有优先级**。把一条队列灌满会让插件自己的控制消息也排在
后面（head-of-line blocking）。要优先级就再开一条队列。

## 八、诊断工具

这台机器上没装调试器，所以运行时自带了两件"卡住时能看"的东西 ——
重写过程中三个死锁就是靠它们定位的。

### `--watchdog <毫秒>`

定期打印：

* 每个插件的状态与 `gen`；
* **哪条资源的锁正被握着**（`Registry::dump_held` 用 `try_lock` 试一把，含 `gen == 0`
  的条目 —— 卸载中途"已经置 0 但锁还没放"正是最需要被看见的状态）；
* 每条队列的 `used/pushed/popped/full/paced` 和**它的线程现在在哪一步**
  （`run:top` / `run:wait-pace` / `run:dispatch` / `d:blocking-lock` / `d:plugin-call` …）。

### `MDPSR_TRACE=1`

打开卸载路径的分步跟踪（`[trace] 3 drop_queue Queue_gamma ...`）。

### `--selftest --cycles N`

一边开 4 条捣乱线程往这些插件里灌消息，一边真的装卸 N 轮，最后核对：
条目/队列回到基线、没有漏还的锁、没有越序借用、**没有任何 handle 返回过失败码**。
接着跑 GUI 阶段（winmsg + 4 个客户端，122 条断言：可见性 / 像素级缩放偏置透明 /
RECT / 模拟点击关闭 / 热插拔）—— 全部在 `test/gui_selftest.cpp`。

### `--guitest`

只跑 GUI 阶段（几秒钟）。改 winmsg 或 GUI 客户端时用它迭代，比整轮压力测试快得多。

## 九、重写过程中抓到的坑

前三个死锁**只在长时间并发热插拔下才出现**，`--cycles 20` 永远碰不到。
它们同源：

> **有人持着锁去 `join()` 一个可能正等着那把锁的线程。**

| # | 现场 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 队列线程卡在 `dispatch_frame` 等 handle 锁；卸载方握着它等 `join` | 队列线程"看过 gen 之后"才去阻塞等锁 | `lock_bounded`：先 try，失败再看 gen；仍然有效才**有界**等待 |
| 2 | 同一个形状，位置在 `Registry::acquire` | 同上 | 同上（同一个执行点） |
| 3 | 卸载时在途的 handle 返回 `12002`（"我的 State 突然没了"） | "先全部置无效，再抢锁"，于是有个窗口让在途调用看到半死不活的插件 | 改成"**先独占 handle → 再置无效 → 再抢其余**"；第一步失败时什么都还没改 |

第四个坑是加 GUI 时抓到的，形状不同（**在一个调用里嵌套借两个资源** → `LOCK_ORDER`），
写在 [GUI.md](GUI.md) 第八节。

第五个是本轮修的，把"持锁 join"这个形状**彻底**关掉：

| # | 现场 | 根因 | 修法 |
| --- | --- | --- | --- |
| 4 | 理论上：卸载 X 时持 `_ctrl_mtx` 去 join X 的队列线程，而那条线程上的插件代码正阻塞在 `_ctrl_mtx` 上 | "持锁 join" 的最后一条边：插件代码也会进管理面 | 插件代码进管理面改成 `try_lock` 一次、失败给 `BUSY`（`sysmgr` 负责重试）；顺带收紧队列归属（`queue_bind` / 运行时 `queue_create`），让"别人的队列线程被 join"这件事本身也不成立 |
| 5 | 装载窗口里被派发的 handle 借不到自己的 State（`11019`，自测抓到 2 次） | 半装好的条目已经挂上表、也能被分发 | 上线门闸（`published`）：READY 之前谁也借不到；分发路径遇到没上线的 handle 回 `BUSY` 让消息重投，而不是当死信丢 |

被压力测试暴露出来的证据长这样（`--watchdog` 的输出）：

```
gamma gen=61 UNLOADING 条目=6
HELD  handle 'gamma.Handle.Work' (gen 0)
Queue_gamma used=4088/4096 pushed=148 popped=2 full=37543  tid=8944 where=run:dispatch
```

—— 进程停在 `[trace] 3 drop_queue Queue_gamma`，`where=run:dispatch`
（后来把标记细化到 `d:blocking-lock` 才锁定是"阻塞等锁"那一步）。

## 十、GUI：为什么它不在宿主里

**用法、参数手册、4 通道图像约定、事件协议、踩过的坑都在 [GUI.md](GUI.md)。**
这里只说它对架构的影响。

### 10.1 宿主主线程不参与分发（v3 的决定）

Win32 的两条硬约束决定了"谁来泵"必须有个答案：

1. 窗口消息只能由**创建窗口的那条线程**收（`PeekMessage` 读的是调用线程的队列）；
2. `WM_PAINT` 是**低优先级合成消息** —— 只有当该线程的 Win32 队列没有别的消息时才合成。
   （框架自己的环形缓冲**不是** Win32 队列，所以它不会挡住 `WM_PAINT` 的合成。）

如果让宿主主线程既泵 Win32 又分发框架消息，那么**一个慢的消息处理器就会直接把界面冻住**
（最轻掉帧，最重 5 秒后系统判定"未响应"，期间任何线程 `SendMessage` 到那个窗口都会死等）。

所以 v3 把"宿主主线程上的队列"**整个删掉**：GUI 变成一个普通插件（`winmsg`）自己开线程。

### 10.2 插件自己开线程 ⇒ 卸载前必须自己 join

框架只 join **它自己建的队列线程**。插件用 `std::thread` 开的线程框架完全不知道 ——
"卸载前 signal + join"是插件自己的责任，忘了就是 DLL 卸掉时线程还在跑（直接崩）。
正确位置是 Object 的 `_destroy`（一定在 `FreeLibrary` 之前，而且池和 Object 都还活着）。

换来的好处是：**慢客户端卡不住界面** —— 客户端的消息处理跑在它自己的队列线程上。

### 10.3 状态还是消息：一条判据

> **每条都要处理、顺序有意义 → 消息；只要最新一版、丢了无所谓 → 状态。**

GUI 把它推到了台面上：同一个插件里**画面走状态**（`content_seq` / `win_seq` 序号，
天然合并重绘）、**事件走消息**（每条都不能丢）、**鼠标位置走状态快照**（一秒上百条，
合并掉才对）。

### 10.4 仍然是"借还协议"在兜底

画面放在**客户端自己的 State** 里，broker 贴图时 `acquire` 它。那把锁在这里主要不是
防撕裂，而是**生命周期押金**：客户端想卸载就得先抢到这把锁，抢不到就 `BUSY` 下轮再来 ——
所以 `pixels` 这个裸指针在整个贴图期间永远有效。

**裸指针可以传，但只能在借到锁的期间用。**

### 10.5 画面参数的语义（缩放 / 偏置 / 系统裁剪）

winmsg 协议 v2 起，客户端只给三样东西：**图像内存**（4 通道 BGRA）、**缩放**
（`scale_x/scale_y`，0 = 1.0）、**偏置**（`img_pos` = **原图左上角**在客户区里的位置，
坐标原点与 Win32 一致：左上角）。

管线固定是"**先缩放 → 再偏置 → 写画布 → 窗口外交给系统裁**"：

* 画布和客户区一样大，初始全 0（透明）；
* 写出画布的点根本不写 —— 所以"图比窗口大""偏置跑到出界"这类情况**不需要任何特判**，
  没画到的地方天然是透明的；
* 采样是最近邻，不插值（要平滑由客户端自己先缩放好）。

参数手册、事件表、踩过的坑、自测清单全在 [GUI.md](GUI.md)。
