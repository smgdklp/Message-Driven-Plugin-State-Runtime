## 一、模块划分

```
mdpsr.exe (宿主)
├── Runtime            引导 / 收尾 / 分发 / 装载 / 日志 / 路径
├── MainMap            一张大表 + 四个二级字典
├── Queue × 3          环形字节缓冲 + 自己的线程 + 限速计时器
├── Pools × 4          Pool_map / Pool_state / Pool_object / Pool_msg
├── Loader             清单解析 + plugin_load / plugin_unload
├── Json               清单与配置的读取器 (只读, 严格)
└── host api           把上面这些装配成函数表交给插件 (host_api.cpp)

插件 (dll)
├── core               core_Handle_Mgr / core_Mgr / core_State_ResourceDict
└── ...                业务组件
```

### 各文件干什么

| 文件 | 职责 |
| --- | --- |
| `src/main/include/mdpsr/abi.h` | **唯一契约**：Ptr、HashMap、Context、host api、命名规范、错误码 |
| `src/main/runtime/mainmap.cpp` | 大表与二级字典、锁、valid 门闸 |
| `src/main/runtime/queue.cpp` | 环形缓冲、组帧、线程、限速 |
| `src/main/runtime/runtime.cpp` | 池、队列、Context 组装、分发、引导、收尾 |
| `src/main/runtime/loader.cpp` | 清单解析、符号推导、装载、卸载 |
| `src/main/runtime/json.cpp` | 清单/配置解析（严格：解析完不允许有多余内容） |
| `src/main/runtime/host_api.cpp` | host 函数表装配 + **逐字段核对** |
| `src/main/main.cpp` | 主程序（很薄） |

### 宿主"不做什么"

宿主里**没有任何一行关于具体业务的代码**。它不知道什么是窗口、什么是图片、
什么是插件装载流程 —— 后者是 `core` 组件干的，而 `core` 只是个普通插件：
它的全部配置写在 `core/plugin.json` 里，由宿主用同一套 `plugin_load` 装进来。

宿主额外认识的东西只有两处，这是设计上的有意妥协：

1. **后门**：`config.json` 的 `init_cmd` 会被 `GetProcAddress` 找到并**直接调用**
   （不经过消息队列）。它存在的唯一原因是"内核自己还没跑起来时，得有人点火"。
2. **点火**：装载完所有插件后，宿主会给每个 handle 投一条 `cmd = 0`。

## 二、消息的生命周期

### 2.1 帧布局

```
偏移   类型       字段
 0     uint64_t   _handle     目标 handle 的哈希
 8     int32_t    _cmd        命令号
12     int32_t    _len        本条消息总字节长 (= 16 + body 长度)
16     uint8_t    body[]      载荷
```

* `_len` 由 `push` 自动算，投递方不需要填。
* 队列**不解释 body**。怎么解析由收件组件自己约束。
* 约定：body 的前 4 字节恒为 `_cmd`；`cmd = 0` 是初始化。

### 2.2 一次投递的完整路径

```
emit(handle_key, body, len)
  │
  ├─ 查这个 handle 绑在哪条队列 (_handle_queue)
  │    └─ 没绑 -> 用它所属插件的默认队列
  │         └─ 还没有 -> Queue_default
  │
  ├─ 从 body 前 4 字节取 _cmd
  ├─ Queue::push(handle_key, cmd, body, len)   ← 组帧 + 写环形缓冲 (持锁)
  └─ 唤醒等在这条队列上的线程 (notify_one)
       │
       ▼
  Queue 自己的线程
  ├─ pop 出一条完整消息 (持锁, 拷到 _scratch)
  ├─ 限速: 距离上一条不够 pace_ms 就先睡
  └─ Runtime::dispatch_one(q, handle, cmd, body, len)
       │
       ├─ 从 handle 描述符里取所属插件
       ├─ 算出要锁的键: handle + 该插件声明的 state / object
       ├─ MultiLock 按键升序取锁
       │    └─ 有一把拿不到 -> 把这条消息回滚到同一条队列, 返回 BUSY
       ├─ 复查 handle 是否还有效
       ├─ 组装 Context (四个二级字典 + host)
       ├─ 调用 handle 函数 (异常一律接住)
       ├─ 释放全部锁          ← 调用一返回就放
       └─ 非 OK 就记一条 WARN + dispatch_errors++
```

### 2.3 三条队列

| 队列 | 谁建的 | 跑法 | 用途 |
| --- | --- | --- | --- |
| `Queue_pluginmgr` | `core` 的后门 | 常驻线程 | 内核专用：装载 / 卸载 |
| `Queue_default` | 宿主 `init` | 常驻线程 | 没声明 `Queue` 的 handle 都走这条 |
| `Queue_windowsgui` | 宿主 `init` | **挂主线程** | GUI 组件专用 |

`Queue_windowsgui` 不起自己的线程：它的 `pump_once()` 由宿主主循环反复调用。

```
主循环 (main.cpp) = 泵 Win32 消息 -> pump_main(0) -> 睡 1ms -> 循环
```

**为什么必须这样**：Win32 规定窗口只能被创建它的那条线程处理消息，而且那条
线程必须自己泵消息。把窗口建在普通分发线程上，它收不到鼠标点击，别人
`SendMessage` 过来还会直接死等。

### 2.4 限速计时器

`Queue` 自带 `pace_ms`：两条消息的**处理开始时间**之间至少隔这么久。

* 普通队列：到点之前在**自己那条线程上**睡（不影响生产者，`push` 只需要那把锁）。
* 主线程队列：到点之前**直接返回 0**，让主循环下一轮再来 —— 绝不能在主线程上
  `sleep`，那会把 Win32 消息泵堵死。消息留在队列里不动，顺序不会乱。

对自转循环（把消息回滚给自己的组件）来说，限速就是"最多跑到 1/pace_ms 次每秒"。
**但这是保险，不是许可** —— 组件自己该有终止条件（见 ticker 的"跑够 50 拍收工"）。

## 三、初始化与收尾时序

### 3.1 启动

```
main()
 ├─ Runtime::init(root)
 │    ├─ 建四个池: Pool_map / Pool_state / Pool_object / Pool_msg
 │    ├─ 记下主线程 id
 │    └─ 建三条固定队列 (顺序固定):
 │         1. Queue_pluginmgr   缓 4096,  pace 0,  专属线程
 │         2. Queue_default     缓 65536, pace 0,  专属线程
 │         3. Queue_windowsgui  缓 16384, pace 8,  挂主线程
 │
 ├─ Runtime::boot()
 │    ├─ 读 exe 同目录 config.json
 │    ├─ 按 plugin 列表顺序逐个 plugin_load
 │    │     (LoadLibrary -> ABI 核对 -> module_init -> 建队列 ->
 │    │      State 工厂 -> Object 工厂 -> 注册 Handle -> 登记插件条目)
 │    ├─ 调 init_cmd 指定的后门, 在所有已加载模块里找同名导出
 │    │     (core_Handle_Mgr: 建 Queue_pluginmgr + 绑定 + 投第一条 cmd=0)
 │    └─ 给每个不在 pluginmgr 上的 Init handle 投一条 cmd=0 点火
 │
 └─ 主循环
```

两点值得注意：

* **`config.json` 的 `plugin` 顺序就是依赖顺序**。排在前面的先装好，后面的在
  自己的 `cmd=0` 里才能看到前面的 State。顺序错了不会报错，只会"看不到"。
* **后门先于点火**。后门负责把内核自己立起来（含建立 `Queue_pluginmgr`），
  点火才是普通组件的初始化。

### 3.2 收尾

```
Runtime::shutdown()
 ├─ stop_queue_threads()      给每条队列 request_stop, 然后 join
 │     └─ 顺序是硬要求: 线程必须在 FreeLibrary 之前停干净,
 │        否则它可能正跑在插件代码里, 而 dll 已经被卸掉
 ├─ 反序 plugin_unload 每个插件
 └─ 汇总计数 (入队 / 分发 / 限速挡下 / 错误)
```

> 退出码本身在正常路径下是 0；如果看到 `0xC0000374`（堆损坏）之类，
> 说明某处的分配与释放不配对 —— 见 [六、内存与池](#六内存与池)。

## 四、并发模型

### 4.1 三层锁，各管各的

| 锁 | 保护什么 | 谁用 |
| --- | --- | --- |
| `MainMap::_mtx`（`shared_mutex`） | **表的形状**：查找 / 插入 / 摘除 | 全部线程。查表共享、插入摘除互斥 |
| `Queue::_mtx` | 环形缓冲的读写游标、扩容、`_scratch` | 多生产者 + 单消费者 |
| `Ptr::mtx` | **"这个资源正在被使用"** | 分发路径与卸载路径 |

**`Ptr.mtx` 不是用来保护数据字段的** ——它是"占用声明"。所以：

* 只想看一眼：读 `valid` 就够了，不碰锁。
* 要真正用了：持锁，并在持锁期间复查 `valid`（拿锁的过程中可能刚好被置无效）。
* 拿不到锁：**不要忙等**。分发路径回滚消息，卸载路径报 BUSY 等下一轮。

### 4.2 为什么不会死锁：按键升序

分发要拿多个锁（handle + 声明的 state/object），卸载要拿一整个插件的锁。
两边**都**走同一个顺序：

```cpp
// MultiLock 内部: 按键升序排好再逐个 try_lock
std::sort(items.begin(), items.end(),
          [](const Item& a, const Item& b) { return a.key < b.key; });
```

顺序一致 ⇒ 不可能出现"A 等 B、B 等 A"的环。这也是为什么 `MultiLock::acquire`
和 `acquire_raw` 共用同一段排序逻辑 —— 两份实现迟早会走偏。

**全有或全无**：一把拿不到就把已拿到的全部放掉。调用方不需要处理"半个资源"。

### 4.3 谁在什么线程上

| 线程 | 跑什么 |
| --- | --- |
| 主线程 | Win32 消息泵 + `Queue_windowsgui` 的 handle |
| `Queue_pluginmgr` 线程 | `core_Handle_Mgr`（装载/卸载） |
| `Queue_default` 线程 | 所有没声明队列的 handle |
| 每条自申请队列 | 各自声明绑上去的 handle |

**同一条队列上的消息天然串行**（一个 dispatcher 一次只处理一条），
**不同队列之间是真并发**。

### 4.4 分发期间持锁的后果

handle 在被调用时，**它自己和它声明的 state/object 都被锁着**。这意味着：

* 别的线程想用同一个资源 → 拿不到锁 → 那条消息被回滚重试。这是**有意**的：
  宁可让消息等，也不让两个线程同时改同一份数据。
* handle 里**不要**去写自己已经声明的 state —— 那等于在持锁时再拿同一把锁。
  `std::mutex` 不可重入。要改就让持有该 state 的那个 handle 去改。
* handle 里**不要长期阻塞**（`sleep`、等 IO）。你占着锁，别人就得重试。

## 五、装载与卸载

### 5.1 清单解析（`load_manifest`）

* `name` 必须存在且不超过 63 字节。
* `dll_path` 是**相对本清单所在目录**的路径，可以是字符串或数组。
* `State` / `Object` / `Handle` / `Queue` 接受 `"X"` 或 `["X","Y"]` 两种写法。
* `Handle` 至少要有一个；`Init` 写了就必须指向一个声明过的 Handle。
* 解析是**严格**的：JSON 顶层值之后不允许有多余内容，数字格式非法直接报错。

### 5.2 符号推导

条目名是给人看的字符串，导出符号名由它推出来：

```
State  "Ticker.Ticks"        -> mdpsr_state_Ticker_Ticks
Object "Ticker.Keeper"       -> mdpsr_object_Ticker_Keeper (+ _destroy)
Handle "Ticker.Handle.Tick"  -> mdpsr_handle_Ticker_Handle_Tick
Queue  "Queue_ticker"        -> mdpsr_queue_Queue_ticker
```

规则：**非 `[A-Za-z0-9_]` 的字符统一变成 `_`**。

> ⚠ 规范化之后必须仍然唯一。`A.B` 和 `A_B` 会推出同一个符号 —— 加载器目前
> **不检查**这种冲突，会静默命中其中一个。条目名别在这种地方含糊。

### 5.3 装载做了什么

```
plugin_load(manifest_rel)
 ├─ 解析清单 (已解析过就直接用)
 ├─ 已加载? -> ALREADY_EXISTS (不报错, 调用方自己决定怎么处理)
 ├─ 逐个 dll: LoadLibrary -> 核对 mdpsr_abi_version -> 调 mdpsr_module_init
 ├─ 建插件自己申请的队列 (Queue 段里不是三条固定队列的那些)
 ├─ State 工厂  -> 载荷进 Pool_state  -> attach(STATE)
 ├─ Object 工厂 -> 实例进 Pool_object -> attach(OBJECT)
 ├─ Handle      -> 描述符进 Pool_object -> attach(HANDLE)
 │                 并记下"这个 handle 归哪个插件"、"默认走哪条队列"
 └─ 插件条目    -> attach(OBJECT, key = hash("plugin:<插件名>"))
                   资源键里会带上它, 但 plugin_keys() 会把它滤掉
```

任何一步失败都只是 `continue` + 日志，**不中断整个装载**。所以"装载成功但少了
一半资源"是可能的 —— 排错时看日志里有没有 `找不到导出`。

### 5.4 卸载做了什么

顺序是设计出来的，每一步都有理由：

```
plugin_unload(plugin)
 0. 先把 (键, Ptr) 抄下来
      因为第 1 步会把它们全部置无效, 之后 map_get 就再也拿不到了
 ├─ 拒绝卸自己: 如果本插件的队列线程就是当前线程 -> BUSY
 │    (join 自己 = 死锁)
 ├─ 1. 全部条目 valid = false      ← 挡住所有新的 get()
 ├─ 2. 按键升序 try_lock 全部条目
 │      拿不到 -> 把 valid 恢复回去, 返回 BUSY
 │      ★ 恢复是必须的: 否则这个插件会"既跑不了也卸不掉", 那是最糟的状态
 ├─ 3. 停掉这个插件自己的队列 (request_stop -> join)
 │      join 必须在 FreeLibrary 之前
 ├─ 4. 释放资源
 │      Object -> 调插件的 _destroy -> 还回 Pool_object
 │      Handle -> 析构描述符 -> 还回 Pool_object
 │      Queue  -> 从队列表摘掉 -> 析构 -> 还回 Pool_object
 │      State  -> 只摘表 (载荷在统一 Pool_state 里, 见下)
 ├─ 5. detach 全部键 + 清 owner/queue 映射
 └─ 6. mspsr_module_fini -> FreeLibrary
```

**为什么"能拿到锁就可以直接删"**：锁是"正在使用"的唯一判据。在第 2 步全部
拿到锁的那一刻，可以确定没有任何线程正持有这些资源 —— 因为在第 1 步之后新的
获取全部失败，而在第 1 步之前开始的获取必须持锁、也就挡住了第 2 步。所以
拿到锁 = 没人在用 = 可以直接删。

**"卸载推迟"的完整闭环**（`core` 侧）：

```
core_Handle_Mgr 收到 cmd=2
  └─ core_Mgr 调 plugin_unload
       ├─ OK   -> 从资源字典里删掉这个插件, 记一条完成日志
       └─ BUSY -> 不是错, 是"还没轮到"
            ├─ core_Mgr 报 need_retry
            ├─ handle 把这条 cmd=2 原样 queue_emit 回 Queue_pluginmgr
            └─ 计数超上限 (kMaxRetry = 40) 才放弃并返回 PLUGIN_BUSY
```

### 5.5 为什么没有"重载"

`plugin_load` 对同一个插件名返回 `ALREADY_EXISTS`，`plugin_unload` 之后**没有**
重新加载的路径。当前骨架的选择是"装进来就用到进程结束"。

如果以后要加重载，必须先解决：

* `Ptr` 条目的**代际**问题（detach 之后同名重新 attach，旧指针不能复活）。
* `Pool_state` 里的载荷不释放（见 [六](#六内存与池)），重载会累积。

## 六、内存与池

### 6.1 四个池各装什么

| 池 | 装什么 | 生命周期 |
| --- | --- | --- |
| `Pool_map` | `mdpsr_ptr` 条目、条目名的副本 | 进程 |
| `Pool_state` | **State 的载荷**（公用数据对象） | 进程 |
| `Pool_object` | Object 实例、Handle 描述符、Queue 本体 | 进程（但单个对象会被析构） |
| `Pool_msg` | 环形缓冲、消息字节流 | 进程 |

四个都是 `std::pmr::synchronized_pool_resource` —— 多线程会并发从它们分配，
所以必须是同步的。

### 6.2 谁负责分配

**插件的工厂函数必须用上下文给的那个池**：

| 工厂 | 拿到的池 |
| --- | --- |
| `mdpsr_state_<名>` | `ctx->pool` == `Pool_state` |
| `mdpsr_object_<名>` | `ctx->pool` == `Pool_object` |
| `mdpsr_queue_<名>` | `ctx->pool` == `Pool_msg` |

用错池的后果是**卸载时收不回来** —— 宿主按池的归属去释放，认错了就漏。

### 6.3 分配与释放必须配对

```cpp
// 工厂: 从池里分配
void* mem = ctx->pool->allocate(sizeof(Keeper), alignof(Keeper));
auto* o = new (mem) Keeper(...);

// 析构: 先取池, 再析构, 再还回去
//   ★ 池指针必须在调用析构之前取 —— 析构之后就取不到了
std::pmr::memory_resource* pool = o->pool();
o->~Keeper();
pool->deallocate(o, sizeof(Keeper), alignof(Keeper));
```

> **不要用 `polymorphic_allocator::new_object` 配 `delete`。**
> 那样对象是池出来的、释放走堆，会直接造成堆损坏（退出码 `0xC0000374`）。
> 骨架早期版本就踩了这个坑，现在两个组件都用显式 `allocate` / `~T()` / `deallocate`。
>
> 同理，`new_object` 配 `delete_object` 是配对的，但要求**析构时必须能重新找到
> 那个池** —— 所以要么把池存进对象，要么一开始就别用 `new_object`。

### 6.4 State 的载荷不单独释放

`Pool_state` 里的载荷**没有做逐条释放**：条目 detach 了，载荷还留在池子里，
池的生命周期与进程一致。

* 纯 POD 的 State 载荷（如 `core_State_ResourceDict`、`Ticker.Ticks`）这样完全没问题。
* 如果 State 载荷里放了 `std::pmr` 容器，它们分配的节点同样留在池里。
* **所以频繁装载/卸载同一个插件会累积内存。** 当前不支持重载，影响有限。
* `mdpsr_state::destroy` 字段**存在但从不被调用** —— 别把清理逻辑押在它上面。
  全仓库 grep `->destroy` 没有任何命中点。

### 6.5 HashMap 的稳定性保证

`mdpsr_map`（`HashMap`）是开放寻址 + 线性探测，**永不真正删除**（要删就留
tombstone）。这带来了一个关键性质：

> 条目一旦插入就**绝不搬动**，所以 `mdpsr_ptr*` 可以安全地裸传。

这是 `Context` 里那几个裸指针能用的前提。另外它从不收缩，所以 `find()` 返回的
地址在下次插入之前一直有效 —— 但**别依赖这一点**：真正的保证来自 `Ptr.mtx`。

### 7.2 各处的失败语义

| 场景 | 行为 |
| --- | --- |
| handle 返回非 OK | 记一条 WARN + `dispatch_errors++`。**消息被丢弃，不重试** |
| handle 抛异常 | 宿主接住，记 ERR，按失败处理。**异常绝不穿过 dll 边界** |
| 目标 handle 不存在 / 已失效 | 丢弃 + `dispatch_errors++` + WARN |
| 分发时拿不到资源锁 | 把消息**回滚到同一条队列**，返回 BUSY（这条**会**重试） |
| 队列投递不进 | 回落到 `Queue_default` |
| 清单里某个符号找不到 | 记日志 + 跳过这一项，**装载继续** |
| 插件装载失败 | 记日志 + 继续装下一个（`boot` 不中断） |
| 后门找不到 | 记 WARN，不算错 |

### 7.3 排错时先看哪里

1. **`core_State_ResourceDict`** —— 它是"现在挂着哪些插件"的唯一权威记录。
2. **收尾那行汇总**：`入队 / 分发 / 限速挡下 / 错误`。入队和分发差得多说明有
   消息没被消费；错误数非 0 说明有 handle 返回了非 OK。
3. **`--log <文件>`** 把日志写盘，配合 `--quiet` 只看 WARN 以上。

## 八、已知边界

诚实列一下当前**没做**和**做得不够**的地方，免得踩了以为是 bug：

| 项 | 现状 |
| --- | --- |
| **没有重载** | 卸载之后不能重新装载同一个插件。见 [5.5](#55-为什么没有重载) |
| **State 载荷不释放** | `Pool_state` 只增不减。频繁装卸会累积内存 |
| **符号规范化不查重** | `A.B` 与 `A_B` 会推出同一个符号，加载器不报错 |
| **`object_destroy` 是空壳** | host api 里这个函数固定返回 `NOT_FOUND`；实例析构统一走卸载路径（要调插件的 `_destroy`） |
| **`emit` 的队列选择很窄** | 只支持"handle 绑定的队列"和"所属插件的默认队列"，**没有**按 handle 单独配置 |
| **`queue_list` 不报限速** | 只能拿到队列键，拿不到 `pace_ms` |
| **帧长上限 64MB** | `Queue::push` 超过就**静默丢弃**，不返回错误 |
| **`push` 的失败不可见** | 空指针 / 超长 / 帧长溢出都只是 `return`，调用方拿不到 |
| **整帧损坏只丢帧头** | 不整条队列清空（比旧版好），但损坏的那条消息会丢 |
| **插件资源上限** | `core` 的资源字典是 64 插件 × 64 项，超了只记前 64 项 |
| **没有 32 位构建** | `static_assert` 只保证了 x64 的尺寸；换平台要重算 |
| **`mdpsr_map` 的成员是公开的** | 插件**可以**绕过 host api 直接调 `find`/`set`。规范禁止，但没有强制 |

### 一个已经修掉的、值得记住的坑

分发时**不要**通过"哪个插件声明了这个 handle"反查所属插件 —— 那种查表在
多插件场景下容易拿到别的插件（骨架早期版本就因为这个，用 ticker 的清单去组装
core 的 Context，导致 core 找不到自己的 Object）。

正确做法：**handle 描述符里自己就存着 `plugin` 字段**，直接用它。
权威信息放在离数据最近的地方，不要靠反查。
